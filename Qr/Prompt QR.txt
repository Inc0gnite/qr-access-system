Quiero que me ayudes a construir un sistema fullstack de control de acceso con QR. 
A continuación te detallo todo lo que necesitas saber antes de empezar.

## Descripción del proyecto
Sistema web que permite registrar entradas y salidas de personas (empleados, 
visitantes, contratistas) mediante códigos QR únicos. Incluye panel de 
administración, historial de accesos, alertas y reportes exportables a Excel.

## Stack tecnológico
- Frontend: React + TypeScript + Zustand + TanStack Query
- Backend: Node.js + Express (funciones serverless en Vercel)
- Base de datos: PostgreSQL en Neon con Prisma ORM
- Autenticación: JWT (también usado dentro del token QR)
- Librerías: qrcode, html5-qrcode, ExcelJS, Zod, dotenv
- Deploy: Vercel (frontend + backend) + Neon (BD)
- CI/CD: GitHub Actions
- Actualización del panel: polling cada 5 segundos (sin WebSockets)

## Modelos de base de datos (Prisma)

model User {
  id            String   @id @default(uuid())
  email         String   @unique
  password_hash String
  rol           String   // "admin" | "guardia"
  created_at    DateTime @default(now())
}

model Person {
  id         String      @id @default(uuid())
  nombre     String
  tipo       String      // "empleado" | "visitante" | "contratista"
  qr_token   String      @unique @default(uuid())
  foto_url   String?
  activo     Boolean     @default(true)
  created_at DateTime    @default(now())
  accesos    AccessLog[]
  alertas    Alert[]
}

model Door {
  id        String      @id @default(uuid())
  nombre    String
  ubicacion String
  activa    Boolean     @default(true)
  accesos   AccessLog[]
}

model AccessLog {
  id        String   @id @default(uuid())
  person    Person   @relation(fields: [person_id], references: [id])
  person_id String
  door      Door     @relation(fields: [door_id], references: [id])
  door_id   String
  tipo      String   // "entrada" | "salida"
  timestamp DateTime @default(now())
}

model Alert {
  id         String   @id @default(uuid())
  person     Person?  @relation(fields: [person_id], references: [id])
  person_id  String?
  tipo       String   // "qr_invalido" | "fuera_horario" | "sin_salida"
  mensaje    String
  leida      Boolean  @default(false)
  created_at DateTime @default(now())
}

## Módulos a desarrollar (en este orden)

### Fase 1 — Base del proyecto
1. Inicializar monorepo con frontend (Vite + React + TypeScript) y backend (Node + Express)
2. Configurar Prisma con Neon (usar variable de entorno DATABASE_URL)
3. Crear migraciones y seed básico de datos
4. Configurar dotenv y estructura de variables de entorno
5. Configurar GitHub Actions con un workflow básico de lint y build

### Fase 2 — Autenticación
1. Endpoint POST /api/auth/login que recibe email y password
2. Retorna JWT con id, email y rol del usuario
3. Middleware de autenticación que valida el JWT en rutas protegidas
4. Middleware de autorización por rol (admin vs guardia)
5. En frontend: página de login, store de Zustand para sesión, 
   redirección según rol

### Fase 3 — Gestión de personas
1. CRUD completo de personas (GET, POST, PUT, DELETE)
2. Validación de todos los campos con Zod en el backend
3. Al crear una persona, generar automáticamente su qr_token único
4. Endpoint GET /api/persons/:id/qr que retorna la imagen del QR 
   generada con la librería qrcode
5. En frontend: tabla de personas con filtros, formulario de 
   creación/edición, botón para descargar QR como PNG

### Fase 4 — Escáner y registro de accesos
1. Endpoint POST /api/access/scan que recibe { qr_token, door_id }
2. Lógica: buscar la persona por qr_token, verificar que esté activa,
   determinar si es entrada o salida (alternar según último registro),
   guardar en AccessLog, retornar resultado
3. Si el QR no existe o la persona está inactiva, crear una Alert 
   de tipo "qr_invalido"
4. En frontend: página de escáner usando html5-qrcode con la cámara,
   mostrar respuesta visual (verde = válido, rojo = inválido),
   selector de puerta activa

### Fase 5 — Panel en tiempo real (polling)
1. Endpoint GET /api/access/live que retorna las últimas 20 entradas/salidas
2. Endpoint GET /api/access/inside que retorna quiénes están dentro ahora
3. En frontend: dashboard con polling cada 5 segundos usando TanStack Query
   (useQuery con refetchInterval: 5000), tabla de accesos recientes y 
   contador de personas dentro

### Fase 6 — Alertas
1. Endpoint GET /api/alerts que retorna alertas no leídas
2. Endpoint PATCH /api/alerts/:id/read para marcar como leída
3. En frontend: badge con contador en el menú, panel de alertas 
   con listado y botón para marcar como leída

### Fase 7 — Reportes
1. Endpoint GET /api/reports/attendance?from=&to= que retorna 
   asistencia por persona en un rango de fechas
2. Endpoint GET /api/reports/export que genera y retorna un 
   archivo .xlsx con ExcelJS
3. En frontend: selector de fechas, tabla con resumen de horas 
   por persona, botón de exportar a Excel

### Fase 8 — Gestión de puertas
1. CRUD de puertas (nombre y ubicación)
2. Activar/desactivar puertas
3. En frontend: tabla de puertas con formulario de creación/edición

## Seed de base de datos
Crear un archivo seed.ts con:
- 1 usuario admin y 1 usuario guardia
- 10 personas de prueba (mix de empleados y visitantes)
- 3 puertas
- 30 registros de acceso de los últimos 7 días
- 5 alertas de ejemplo

## Seguridad adicional
- Si el JWT expira, redirigir automáticamente al login sin romper la app
- El token QR de una persona inactiva debe ser rechazado aunque el JWT sea válido
- Los endpoints de admin no deben ser accesibles con rol guardia

## Reglas generales de desarrollo
- Usar TypeScript estricto en frontend y backend
- Validar todos los inputs con Zod antes de tocar la base de datos
- Manejar errores con try/catch en todos los endpoints
- Usar variables de entorno para toda configuración sensible
- El código debe estar comentado en español
- Nombrar variables, funciones y endpoints en inglés

## Lo que NO hay que hacer
- No usar Socket.io ni WebSockets
- No usar Redux (usar Zustand)
- No hardcodear URLs ni credenciales
- No saltarse las validaciones con Zod

Quiero avanzar este proyecto fase por fase. Al finalizar cada fase 
avísame antes de continuar con la siguiente, ya que trabajaré cada 
fase en una conversación separada para evitar que el contexto 
acumulado consuma tokens innecesarios y asegurar un ritmo de trabajo 
continuo sin interrupciones. Empieza por la Fase 1.
